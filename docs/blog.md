# وبلاگ اومینی‌کورپ: طرح و معماری

صفحهٔ اصلی فقط لینک وبلاگ می‌گیرد. وبلاگ و پنل از همان وب‌سرور Node و دارایی‌های محلی استفاده می‌کنند، بدون SPA یا CDN. دو ترجمهٔ کامل، یک رکورد تحریریه هستند و با هم منتشر می‌شوند. `server/blog/schema.mjs` قرارداد مشترک فرم ادمین، ذخیره‌سازی، مدل و MCP است؛ `store.mjs` migration، مقاله و تنظیمات را نگه می‌دارد؛ `render.mjs` صفحات عمومی و SEO و `admin.mjs` صفحات پنل را می‌سازند؛ `routes.mjs` احراز هویت پنل و مسیرها را هماهنگ می‌کند؛ `mcp-http.mjs` راهنمای مرورگر، CORS و احراز هویت MCP را مدیریت می‌کند؛ `automation.mjs` RSS/Atom، کلاینت AI، حذف موارد تکراری و زمان‌بندی را پیاده می‌کند؛ `mcp.mjs` از SDK رسمی برای سرویس Streamable HTTP استفاده می‌کند. `seed.mjs` محتوای نمونهٔ اختصاصی، `assets/blog.css` طراحی مشترک و `assets/blog-admin.mjs` تعامل‌های کوچک پنل هستند. تست‌های `tests/blog.test.mjs` و `tests/blog.browser.mjs` قراردادها و ظاهر/گردش کلیدی را می‌سنجند.

پنل قابلیت‌های وبلاگ، AI، زمان‌بندی، انتشار خودکار، MCP و دسترسی نوشتن/انتشار MCP را جدا تنظیم می‌کند. تنظیمات در پنل ذخیره می‌شوند. رمز ادمین و توکن MCP هش می‌شوند و مقادیر حساس از UI برگردانده نمی‌شوند. از یک SQLite مستقل در همان volume استفاده می‌شود. معماری تک‌نمونه است؛ برای زمان‌بندی چند replica، قفل/صف توزیع‌شده لازم است. صفحات SSR و sitemap از فقط مقاله‌های منتشرشده ساخته می‌شوند. رتبه و سرعت ایندکس توسط موتور جستجو تعیین می‌شود و تضمین‌شدنی نیست.

## راه‌اندازی و استفاده

۱. `docker compose up -d --wait` و سپس `docker compose exec website node server/setup.mjs`. در `/admin/setup` کد ۱۵دقیقه‌ای، مبدأ واقعی سایت و رمز دلخواه (حداقل ۱۶ نویسه) را وارد کنید. روی تولید از HTTPS استفاده کنید؛ HTTP فقط روی loopback برای توسعه پذیرفته می‌شود. بعد از راه‌اندازی، رمز در `/admin/system` با تأیید رمز قبلی قابل تغییر است.
۲. فارسی `/blog`، انگلیسی `/en/blog` و تحریریه `/admin`. فایل SQLite `blog.sqlite` کنار دیتابیس خبرنامه در volume است. با توقف تمیز کانتینر هر دو فایل را پشتیبان بگیرید. در دستورهای بازیابی README نام فایل را برای وبلاگ به `blog.sqlite` تغییر دهید. پشتیبان وبلاگ مقادیر حساس سرویس‌ها را دارد و باید خصوصی و رمزگذاری‌شده نگهداری شود. نشست‌ها با راه‌اندازی مجدد یا تغییر رمز از بین می‌روند.
۳. برای تولید داخلی، در «تنظیمات سایت ← هوش مصنوعی» نشانی **کامل** `https://…/v1/chat/completions`، شناسهٔ مدل پشتیبان `response_format: {type: "json_object"}` و حداکثر ۱۲ خوراک HTTPS معتبر RSS/Atom وارد کنید. کلید API و نشانی پراکسی دارای نام‌کاربری/رمز را در همان بخش ذخیره کنید. نشانی دارای رمز بر نشانی بدون رمز اولویت دارد. پراکسی باید HTTP CONNECT را پشتیبانی کند. برای هر دو مقصد RSS و مدل از همان پراکسی استفاده می‌شود؛ کلید AI فقط به مقصد مدل می‌رود. مقصدها را فقط به سرویس‌های قابل‌اعتماد تنظیم کنید؛ `redirect` شبکه دنبال نمی‌شود.
۴. دکمهٔ «تولید پیش‌نویس اکنون» دستی است و هرگز خودکار منتشر نمی‌کند. برای تولید زمان‌بندی‌شده، «زمان‌بندی» را فعال کنید و برای انتشار بدون بررسی، جداگانه «انتشار خودکار» را روشن کنید. مدتی که سایت خاموش است جبران نمی‌شود؛ پردازش پس از شروع بعدی از وضعیت پایدار ادامه می‌یابد. هر دور اخبار دارای تاریخ معتبر در ۱۴ روز اخیر را از جدید به قدیم برمی‌دارد؛ سقف هر اجرا بین ۱ و ۲۰ است، نه تولید اجباری همان تعداد. URL نرمال‌شده، شباهت تیتر منبع و تکرار دقیق تیتر تولیدی بررسی می‌شوند. حذف عمدی مقاله، محدودیت URL آن را آزاد می‌کند. خبرهای مشابه با زبان و تیتر متفاوت ممکن است هنوز به بازبینی انسانی نیاز داشته باشند. خروجی فقط از چکیده و فرادادهٔ خوراک استفاده می‌کند، نه متن کامل سایت خبری؛ منابع را معتبر انتخاب کنید و پیش از روشن‌کردن انتشار مستقیم کیفیت دو زبان را بسنجید.

در «عمومی و حساب»، ایمیل و SMTP، دامنه و دسترسی عمومی وبلاگ را مدیریت کنید. تنظیمات مربوط به هر مقاله همچنان در ویرایشگر همان مقاله است؛ مسیر قدیمی `/admin/settings` به تنظیمات سایت منتقل می‌شود. تنظیمات قبلی و توکن موجود تا زمان لغو یا تعویض حفظ می‌شوند.

## اتصال MCP

- نشانی: `https://<host>/mcp`، **Streamable HTTP بدون session سرور** و پاسخ JSON. احراز هویت برای کلاینت‌هایی که هدر سفارشی پشتیبانی می‌کنند: `Authorization: Bearer <token>`؛ توکن را در «تنظیمات سایت ← MCP» با دکمهٔ «ساخت توکن تصادفی» تولید کنید. توکن فقط یک‌بار نمایش داده می‌شود؛ آن را همان‌جا کپی کنید. تعویض یا لغو، توکن قبلی را فوراً نامعتبر می‌کند. توکن را در URL، چت یا مخزن نگذارید. پروتکل `initialize`، `tools/list` و `tools/call` را SDK رسمی مدیریت می‌کند. درخواست GET/SSE دائمی، OAuth و stdio جزو این استقرار نیستند.
- قابلیت «سرور MCP» را در همان بخش فعال کنید. حالت پیش‌فرض MCP پس از فعال‌سازی فقط `list_articles` و `get_article` برای محتوای منتشرشده است. با «نوشتن»، پیش‌نویس‌ها و `create_article`، `update_article`، `delete_article` و هنگام فعال‌بودن AI، `generate_articles` در دسترس‌اند. «انتشار» دسترسی مستقل `publish_article` و تغییر مقالهٔ زنده را می‌دهد. `create_article` همیشه پیش‌نویس می‌سازد.
- طرح ورودی ابزار در `tools/list` شامل `section`، `author`، `sources` و برای **هر دو** `fa` و `en`: `title`، `slug`، `excerpt`، `seoTitle`، `description`، `tags` و `body` (Markdown) است. وضعیت انتشار ابزار جداگانه است. نامک‌ها پس از نخستین انتشار تغییر نمی‌کنند تا URLهای ایندکس‌شده نشکنند. مقالهٔ ذخیره‌شده را قبل از انتشار می‌توان در هر دو زبان با لینک خصوصی پنل دید.

### عیب‌یابی اتصال MCP

بازکردن `/mcp` در یک تب مرورگر فقط راهنما را نشان می‌دهد؛ ابزارها از طریق `POST` دارای توکن در دسترس‌اند. `/mcp` و `/mcp/` کار می‌کنند. در کلاینت **Streamable HTTP** را انتخاب کنید و `Authorization` را با مقدار `Bearer <token>` بفرستید. اگر کلاینت مستقیماً از صفحهٔ مرورگر دیگری وصل می‌شود، مبدأ دقیق آن (مثلاً `http://localhost:6274`) را در «تنظیمات سایت ← MCP» اضافه کنید. مبدأهای مجاز هم بدون توکن به ابزارها دسترسی ندارند. حالت‌های Legacy SSE یا OAuth-only جایگزین این اتصال نیستند.

برای بررسی دستی، در Bash روی میزبان خودتان نشانی نمونه را عوض کنید؛ توکن در تاریخچهٔ فرمان نوشته نمی‌شود:

```bash
read -rsp 'MCP token: ' mcp_token; echo
printf 'Authorization: Bearer %s\n' "$mcp_token" | curl -i \
  'https://your-docker-domain.example/mcp' -H @- \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  --data '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"manual-check","version":"1.0.0"}}}'
unset mcp_token
```

- `200` با نتیجهٔ `initialize`: اتصال و توکن معتبرند.
- `401`: یا هدر نرسیده، یا توکن معتبر نیست/تعویض شده. اگر همین تست در شبکهٔ داخلی ولی نه از دامنه کار می‌کند، عبور `Authorization` از reverse proxy و مسیر `/mcp` را بررسی کنید. توکن را در URL نگذارید.
- `403`: مبدأ کلاینت مرورگری مجاز نیست. `405`: کلاینت از روش یا حالت SSE ناسازگار استفاده می‌کند. `406`: هدر `Accept` باید هر دو نوع مثال را داشته باشد.
- `404`: MCP غیرفعال است، هنوز توکن ندارد یا دامنه به سرور Docker متصل نیست. GitHub Pages نمی‌تواند MCP را ارائه دهد.

## سئو، استقرار و محدودیت‌ها

- مسیرهای جداگانه با HTML سروری، `canonical`، `hreflang` متقابل (`fa`/`en`/`x-default`)، متای توضیح، Open Graph، `BlogPosting`، `BreadcrumbList`، sitemap و robots. پیش‌نویس در sitemap و مسیر عمومی ظاهر نمی‌شود؛ نتایج جست‌وجو `noindex` هستند. برای شروع crawl، نشانی `/sitemap.xml` دامنهٔ واقعی را در Search Console ثبت کنید. رتبه یا زمان ایندکس قابل تضمین نیست؛ محتوای دقیق و مفید از حجم انتشار مهم‌تر است.
- GitHub Pages نسخهٔ ایستای سه مقالهٔ آغازین را بدون پنل، جست‌وجو یا اتوماسیون ارائه می‌کند. `site/export-blog.mjs` این صفحات و sitemap ایستا را تولید می‌کند. برای پنل، جست‌وجوی واقعی، MCP، AI و انتشار زنده، دامنه باید به reverse proxy کانتینر متصل شود؛ نشانی عمومی را در پنل برابر همان دامنه بگذارید.
- فایل‌های UI، فونت، تصویر و وابستگی‌ها داخل ایمیج‌اند و هنگام اجرای کانتینر نصب یا دانلود نمی‌شوند. اولین **ساخت** ایمیج به رجیستری وابستگی‌ها نیاز دارد. خود AI، خبر و SMTP فقط در صورت تنظیم و فعال‌سازی به سرویس‌های بیرونی اتصال می‌زنند. مسیر `/admin` را پشت HTTPS و ترجیحاً دسترسی مدیریتی محدود نگه دارید؛ زمان‌سنج و محدودیت‌ها تک‌فرایندی‌اند.
